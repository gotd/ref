				Parallel downloads file to given io.WriterAt.

			
				Stream downloads file to given io.Writer.
				NB: in this mode download can't be parallel.

			
				ToPath downloads file to given path.
				
				If offset is set (see WithOffset), existing file is not truncated, so data
				before offset is kept. If size is set (see WithSize), the file is truncated
				to it after a successful download.

			
				Verify checks local file data (e.g. a partially downloaded .part file)
				against file hashes from the server (upload.getFileHashes) and returns the
				length of the longest verified prefix.
				
				The r must contain the first size bytes of the file. A trailing part
				shorter than a hash window can be verified only if it is the end of the
				file, otherwise it is not counted.
				
				If the result equals the file size (e.g. Document.Size), the local file is
				complete: do not resume. Otherwise the result ends at a hash window border,
				which is 4KB-aligned, and can be passed to WithOffset to resume a download
				safely together with WithVerify(true). Without verification, WithOffset
				requires the offset to be divisible by the part size, so round the result
				down to it:
				
					off -= off % partSize

			
				WithOffset sets offset to start download from, e.g. to resume a partially
				downloaded file. Data before offset is not downloaded.
				
				Offset must be divisible by the part size (see Downloader.WithPartSize),
				unless verification is enabled via WithVerify(true), which only requires
				4KB alignment: the hash window containing offset is downloaded whole to
				verify it, and data before offset is dropped.
				
				Stream writes data from offset to the start of io.Writer, Parallel writes
				it at the same offsets of io.WriterAt, and ToPath keeps existing file
				content before offset.

			
				WithProgress sets callback called after each written part.

			
				WithRefresh sets callback to refresh file location on file reference
				errors (FILE_REFERENCE_*), so download continues from the same offset
				instead of failing.
				
				Concurrent workers share one refresh, and a request is retried at most
				three times. Has no effect for web files.

			
				WithRetryHandler sets callback for transient download errors that are retried
				internally.
				
				Handler can be called concurrently from download workers.

			
				WithScheduler sets Scheduler for this download, overriding the one set via
				Downloader.WithScheduler.

			
				WithSize sets known file size (e.g. Document.Size), so download stops
				requesting parts at the end of file instead of probing past it, and
				progress reports the total.

			
				WithThreads sets downloading goroutines limit.

			
				WithVerify controls global hash verification behavior.
				
				`true` enables classic verifier reader (preloads hash queue and validates all
				chunks, both legacy and CDN).
				`false` disables classic verifier reader.
				
				If not called explicitly:
				- non-CDN path preserves old behavior (no upfront hash requests);
				- CDN path enables strict inline CDN verification after redirect.
				
				Use WithVerify(true) to force verifier-queue mode on all paths.

		Scheduler is an adaptive limit of in-flight part requests shared by
		downloads, like the per-DC download window of Telegram Desktop.
		
		The window grows by one after each window of successful requests and is
		halved on flood wait or timeout, at most once per window of requests in
		flight: concurrent requests failing together halve it once.
		
		Flood waits and timeouts that the CDN download path retries internally,
		e.g. when refreshing an expired redirect via master DC, decrease the window
		too, while the request keeps its slot. Repeated timeouts of one request
		decrease it at most once.
		
		Use one Scheduler per DC (or per connection pool), and pass it to downloads
		via Downloader.WithScheduler or Builder.WithScheduler; Builder.WithThreads
		still limits workers of one download, so set it high enough to fill the
		window.

		
			
			decreases int64
			
				epoch is incremented on each window decrease: a request acquired
				before the last decrease does not decrease the window again, so a
				burst of failures of concurrent requests halves it once.

			inFlight int
			mux sync.Mutex
			opts SchedulerOptions
			successes int
			waiting int
			
				wake is closed and replaced when a slot may become available.

			window int
		
			
				Instrument registers observable instruments of Scheduler state on m:
				gotd.downloader.scheduler.window, .in_flight and .waiting gauges and the
				.decreases counter, with given attributes (e.g. DC).
				
				Unregister the returned registration when the Scheduler is not used
				anymore.

			
				Snapshot returns current state.

			
			
				acquire takes a slot, returning the epoch to pass to release.

			
				backoff decreases window on flood wait or timeout of a request that is
				retried internally while holding its slot, e.g. by the CDN download path.
				
				Returns the epoch to use for further reports and release of this request.
				A flood wait is an explicit signal of the server, so each one of a request
				retried for a long time can decrease the window again. A timeout is not:
				repeated timeouts of one stuck request decrease the window at most once.

			
				decrease halves window, unless it was already decreased after the request
				with given epoch was sent. Must be called with mux held.

			(*Scheduler) notify()
			
				release releases slot taken by acquire, adapting window by request result.
